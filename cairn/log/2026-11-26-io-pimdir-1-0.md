# calendula follows io-pimdir 1.0.0

Calendula moves to io-pimdir 1.0.0, which follows pimdir storage-v1.0.0, sync-v1.0.0 and search-v1.0.0. The dependency and the dev-dependency name `version = "1.0.0"`, from crates.io.

- **Stores**: a store any io-pimdir 0.x release wrote is a draft's store, refused `store-version` and never migrated; there is no migration guide, users start over: sync it with the last 0.x sync engine until nothing is queued, move it aside, and let the new engine create and sync a new one. A later store is judged by its `store_meta` row alone (STORAGE §4.2): the reader and the producer open it while its floors allow, and the owner of `pimdir queue cancel` refuses it. Guarded by `a_store_calendula_cannot_open_carries_its_code`, which now writes `store_meta` through SQLite (a draft store, a later store opening, a later store with raised floors refused) where it patched a same-length marker in place, `storage-v1` being shorter than a draft's.
- **Index**: an index of an earlier version (any draft's) is still refused `index-version` by the query client, and its sync engine rebuilds it. `a_missing_or_outdated_index_says_to_run_the_sync_engine` writes `index_meta.format_version` through SQLite, for the same reason.
- **API**: `PimdirSearchCursor` and `PimdirSearchSort` are imported from `io_pimdir::search::plan`; `PimdirStore::for_source`, which now returns a `Result`, is unwrapped in the tests that seed a store (no production path calls it). No other breaking change of io-pimdir 1.0.0 reaches calendula: it queues no move or copy (`PimdirMutateError::Unsynced`), builds no `PimdirQueryDateRange`, and matches no `PimdirQueryErrorCode` exhaustively. `source-empty` is not relayed, no calendula path binding a source.
- **Docs**: CHANGELOG, the `StoreVersion` and `IndexVersion` docs, and the `store-version` and `index-version` rows of commands.md.

Capabilities moved: backends (the storage-v1 store, a later store opening while its floors allow), commands (the `store-version` and `index-version` codes).
