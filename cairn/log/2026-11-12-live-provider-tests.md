# Live provider suites

tests/google.rs, tests/microsoft.rs and tests/fastmail.rs run the built binary against the real providers, every test ignored unless `--ignored` is given, change 8 of the-family-standards. tests/common.rs holds what they share, Himalaya's and Cardamum's helpers renamed: `write_config`, `calendula` (the binary with `CALENDULA_TEST_TOKEN` in its environment, its home a TempDir, stdin closed), `failure`, `json`, `json_failure`, `json_check_failure`, `assert_check`, `assert_calendars`, `assert_events` (a failure naming the faulty member, never its value), `sample_section`, `env_var`, `require_env` (every unset name in one failure) and `env_content` (a `_FILE` variable or the content itself). Every account is a provider section of config.sample.toml, its secret read through `["printenv", "CALENDULA_TEST_TOKEN"]`. The existing suites are untouched.

- `anonymous` (a made-up credential, no account touched): Google `gcal_account_check_refused`, `gcal_calendar_list_refused`, `caldav_account_check_refused`, `caldav_calendar_list_refused` on the Google Calendar and Google CalDAV sections; Microsoft `graph_account_check_refused`, `graph_calendar_list_refused` on the Microsoft Graph section; Fastmail `caldav_account_check_refused`, `caldav_calendar_list_refused` on the Fastmail section, its user overridden to alice@example.org (a reserved domain, so no real Fastmail account is tried) and its password the made-up one. `account check` exits 2 with the one backend failed, `calendar list` exits 1 with the failure object, the message holding `HTTP 401` in each: "Calendar API returned HTTP 401: Request had invalid authentication credentials...", "WebDAV server returned HTTP 401: GData invalidCredentials Invalid Credentials" (Google CalDAV), "Microsoft Graph API returned HTTP 401 (InvalidAuthenticationToken): ...", "WebDAV server returned HTTP 401: Incorrect username, password or access token." (Fastmail). The failure `code` is `null` in every case, no stable code naming an authentication refusal.
- `credentialed` (read-only): `account check`, `calendar list` and `event list -s 5` per backend, one token minted per run with io-oauth 0.5.2, a new dev-dependency (`client`, `jwt-bearer`, `rustls-ring`). Google `gcal_*` on a service account token acting as google@pimalaya.org (RFC 7523 section 2.1) for `calendar.events` and `calendar.calendarlist.readonly` alone, `calendar list` holding the primary calendar (its id the subject's address), `event list` reading it. Microsoft `graph_*` on a client credentials token for `https://graph.microsoft.com/.default`, the sample's `msgraph.user-id` set to microsoft@pimalaya.onmicrosoft.com, `calendar list` holding `Calendar` and `event list` reading it: calendula prints `default: false` for every gcal and Graph calendar (the CHANGELOG's "for now"), so the suite finds the default calendar by the name Exchange gives it.
- Google CalDAV stays anonymous: probed before writing the suite, its principal (https://apidata.googleusercontent.com/caldav/v2/) refused a token for `calendar.events` with `calendar.calendarlist.readonly`, and one for `calendar.events` alone, with "WebDAV server returned HTTP 403: GData insufficientPermissions Insufficient Permission" on `account check` and `calendar list`. The Calendar API answered the first token on both listings and refused `calendar list` on the second ("HTTP 403: Request had insufficient authentication scopes."), `calendar.calendarlist.readonly` being the scope `calendarList.list` needs.

.github/workflows/tests.yml gains a `live` matrix job (google, microsoft, fastmail, `fail-fast: false`, `RUST_LOG: debug`), Himalaya's: the anonymous step on every push, the credentialed steps in pimalaya/calendula only and when `HAS_GOOGLE` or `HAS_MICROSOFT` holds, mapping `GOOGLE_SERVICE_ACCOUNT_KEY`, `MICROSOFT_TENANT_ID`, `MICROSOFT_CLIENT_ID` and `MICROSOFT_CLIENT_SECRET` to their `CALENDULA_*` variables; the four org secrets are visible to the repository. actionlint passes.

Run on 2026-11-12 from this machine, Microsoft with the tenant name `pimalaya.onmicrosoft.com` in place of its id, Google with the key's `_FILE` path:

- Anonymous: 8 passed (Google 4, Microsoft 2, Fastmail 2), on the final code too.
- Google credentialed: 3 passed, on the final code too; three calendars listed, the primary among them, and `event list -s 5` returning five events and `nextPage` "2".
- Microsoft credentialed: not passing. On the first run `graph_account_check` and `graph_calendar_list` passed and `graph_event_list` failed with "Microsoft Graph API returned HTTP 504 (UnknownError): unknown Microsoft Graph API error", its events request answered after about 30 seconds, Graph's gateway timeout; run alone it failed the same way. In the four later runs, sequential or not, the same `calendars` request answered twice in 0.5 s and failed nine times with HTTP 502 or 504 after 21 to 30 s, while the anonymous requests were refused in 0.2 s. The events request is the whole calendar at `$top=500` with the projection's `$select` (`cancelledOccurrences` and the body among it) and `$expand` of the stash property, `-s 5` paging locally; whether that query on the shared test mailbox is too heavy for Graph, or the mailbox was degraded by other causes, is not established. No code changed for it.
- A credentialed test without its variables fails naming each one unset: "set CALENDULA_MICROSOFT_TENANT_ID, CALENDULA_MICROSOFT_CLIENT_ID, CALENDULA_MICROSOFT_CLIENT_SECRET to run this test", and "set CALENDULA_GOOGLE_SERVICE_ACCOUNT_KEY or CALENDULA_GOOGLE_SERVICE_ACCOUNT_KEY_FILE to run this test".
- One run of all 14 at `RUST_LOG=debug`, and three of the Microsoft suite, saved each binary's stderr through a temporary hook in the helper, removed after: debug lines in every one, and no hit for the minted tokens or the made-up one (counted in the test process, stdout and stderr), the client secret, a `ya29.` prefix or a JWT, in the saved stderr nor in the test output.

io-oauth brings 26 crates to the test build only (rsa 0.10.0, its key and digest crates, ctutils 0.4.8, io-oauth itself); io-http 0.6.0 is the one the binary already uses. `cargo deny check` passes with no ignore, rsa 0.10.0 carrying no advisory, its duplicate warnings unchanged (getrandom, syn).

Verified: `cargo fmt --check`; clippy `--all-targets --locked -D warnings` clean over the eleven sets of the `features` job, `cargo test --locked` passing over them with the counts of every-feature-set-builds-clean (default and `--all-features` 277, the live tests ignored: 14 there, 5 with `msgraph` alone, 2 with `caldav` alone or beside another TLS provider).
